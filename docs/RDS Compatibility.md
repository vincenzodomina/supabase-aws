# RDS Compatibility

Proposed changes for Auth, PostgREST, S3-backed Storage, and optional Studio/postgres-meta on RDS PostgreSQL. The implementation has a minimal bootstrap and passing Docker tests; RDS compatibility remains unverified.

Target: [Supabase self-hosted/v0.8.3](https://github.com/supabase/supabase/releases/tag/self-hosted/v0.8.3), the latest stable self-hosted release checked on 2026-10-31. Keep its coordinated image versions: Auth `v2.197.0`, PostgREST `v14.18`, and Storage `v1.81.0`. Use [Supabase Postgres 17.6.1.136 SQL](https://github.com/supabase/postgres/tree/17.6.1.136/migrations/db) as the upstream reference; the database remains RDS PostgreSQL 17.6.

**Recommended approach:** commit a small, reviewed set of RDS-compatible SQL migrations and execute them through the existing bootstrap Lambda. Keep Auth and Storage responsible for their own schema migrations. Apply upstream adaptations during development, rather than downloading and rewriting SQL during deployment.

| Existing RDS adaptation | Treatment in this project |
| --- | --- |
| Replace superuser and replication-role setup | Create only the required API/service roles. Preserve AWS-managed roles and administrator attributes. Validate `BYPASSRLS`, role membership, ownership, and grants against RDS. Application roles must not receive `rds_superuser`. |
| Remove Postgres demotion and system-function changes | Exclude `10000000000000_demote-postgres.sql`, `20240124080435_alter_lo_export_lo_import_owner.sql`, and `20251105172723_grant_pg_reload_conf_to_postgres.sql`; these operations belong to the upstream distribution's administration model. |
| Remove unavailable preload libraries | Exclude the `safeupdate`/`supautils` settings from `20220118070449_enable-safeupdate-postgrest.sql` and `20260413000000_fix-authenticator-session-preload-libraries.sql`. Their protections are not provided by this stack. |
| Install compatible extensions | Retain `pgcrypto` and `uuid-ossp`. `pg_tle`, `pgjwt`, and additional extensions are unnecessary for the selected services; add them only for an explicit requirement. |
| Repair schema ownership and permissions | Retain service-owned `auth`/`storage` schemas, JWT helpers, explicit memberships, and necessary object/default grants. Review PostgreSQL 16+ membership options and Studio access. Keep application-table grants explicit. |
| Adapt pooler, replication, analytics, and webhook setup | Omit those components' migrations, roles, slots, and supporting databases. This includes the three PgBouncer migrations dated `20250312095419`, `20250417190610`, and `20251121132723`. |

1. **Complete the upstream SQL review.** Classify the pinned distribution migrations as required, adapted, or excluded for this scope. Carry forward relevant permission and security changes without importing broad platform-administration privileges. Record upstream file references beside adapted SQL and update `NOTICE` where source is reused.

2. **Add the missing compatibility changes.** Restore PostgREST's DDL/drop notification triggers, including the `ALTER TYPE` correction from `20220321174452_fix-postgrest-alter-type-event-trigger.sql`. Align `anon`, `authenticated`, and `service_role` inheritance with `20230529180330_alter_api_roles_for_inherit.sql`; retain `NOINHERIT` for `authenticator`. Review the role-logging migration `20250205060043`, PostgreSQL 16+ grant migration `20250605172253`, Storage grants `20250623125453`/`20250709135250`, and privileged-role migration `20260211120934`; adapt only privileges required by the retained services. Set Storage's existing `DB_INSTALL_ROLES=false` default explicitly.

3. **Keep the file changes small.** Move static role creation and [schema.sql](../src/schema.sql) into a baseline under `src/migrations/`, then add one forward migration for the compatibility corrections. Remove the old schema file after the move. Extend [bootstrap.py](../src/bootstrap.py) to apply these files; keep credential synchronization and key generation separate. Baseline adoption must validate existing objects and preserve service-owned migration history and newer helper definitions.

4. **Track migrations through the existing Lambda.** Reuse its PostgreSQL connection and advisory lock. Store migration IDs, checksums, and application timestamps in a private schema. Apply pending SQL and its history entries transactionally; reject changes to already-applied files. Retries must preserve data and credentials. Extend [deploy.sh](../src/deploy.sh) to include the SQL directory in the deterministic ZIP. The existing artifact hash triggers bootstrap updates through the same CloudFormation stack. No additional migration service, container, or framework is needed.

5. **Preserve the service upgrade boundary.** Auth and Storage run their pinned, unmodified migrations after prerequisites succeed. Review their release changes before every upgrade. Version `v0.8.3` includes [one-way Storage migrations](https://github.com/supabase/supabase/blob/self-hosted/v0.8.3/docker/CHANGELOG.md); require a tested backup/restore or forward-fix plan before upgrading. ECS rollback does not undo database changes. Application migrations remain the consuming project's responsibility.

6. **Verify the behavior at both levels.** Extend the existing Docker/Moto suite for migration ordering, failed-transaction recovery, checksum rejection, retries after service migrations, inherited permissions, and schema changes made while PostgREST is running. A separately approved disposable RDS test must verify fresh installation, upgrade, administrator restrictions, extension availability, event-trigger privileges, service migrations, and optional Studio/meta access. Ordinary PostgreSQL and Moto cannot reproduce AWS's privilege model.

RDS permits custom roles but restricts administrator capabilities; see [AWS role documentation](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.rds_superuser.html). Its administrator can create [event triggers](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.FeatureSupport.EventTriggers.html), which support [PostgREST schema-cache reloads](https://docs.postgrest.org/en/v14/references/schema_cache.html). These capabilities still require verification against the target RDS engine.
