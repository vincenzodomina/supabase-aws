# RDS Compatibility

This stack applies a committed subset of Supabase database prerequisites adapted for RDS. It does **not** download, patch with `sed`, or replay the complete upstream migration tree during deployment. Auth, PostgREST, S3-backed Storage, and optional Studio/postgres-meta define the supported scope. Real RDS compatibility still requires [manual AWS acceptance](Deployment.md#manual-aws-acceptance).

The pinned references are [Supabase self-hosted/v0.8.3](https://github.com/supabase/supabase/releases/tag/self-hosted/v0.8.3) and [Supabase Postgres 17.6.1.136](https://github.com/supabase/postgres/tree/17.6.1.136/migrations/db); the default RDS engine is PostgreSQL 17.6. [NOTICE](../NOTICE) records source attribution. The inventory below describes implemented adaptations and explicit exclusions, not a claim of parity with every upstream migration.

## Execution

1. [deploy.sh](../src/deploy.sh) packages both files under [src/migrations](../src/migrations) with the bootstrap Lambda. Changed package content triggers bootstrap through CloudFormation before services start.
2. [bootstrap.py](../src/bootstrap.py#L68) locks initialization, verifies the applied history, and executes pending SQL in filename order. SQL, history entries, and service-role password updates share a database transaction. The private `supabase_aws.migrations` table records IDs, SHA-256 checksums, and timestamps; changed, missing, or reordered applied migrations fail validation.
3. Auth and Storage then execute their own unmodified schema migrations. Storage's `DB_INSTALL_ROLES=false` setting in [supabase.yaml](../src/supabase.yaml) leaves role provisioning to bootstrap. Application migrations remain the consuming infrastructure's responsibility.

Baseline adoption validates existing role attributes, administrator memberships, schema owners, extension locations, and helper signatures. It preserves compatible Auth helper definitions and service migration histories; it is not an automatic conversion of an arbitrary existing Supabase database. Subsequent deployments skip applied SQL rather than continuously repairing database drift.

## Upstream updates and verification

Start an upgrade review from the pinned references above and the image versions in [supabase.yaml](../src/supabase.yaml). Record the old and proposed tags and resolved commit/image digests in the upgrade PR. Compare complete source trees, including added, removed, and renamed files; this inventory is a map of selected behavior, not a filter for discovering changes.

| Compare between releases | Review outcome |
| --- | --- |
| Supabase Postgres `migrations/db/init-scripts` and `migrations/db/migrations` | Classify relevant role, ownership, privilege, extension, helper, and event-trigger changes as retained, adapted for RDS, or excluded with a scope/restriction reason. Review changed defaults as well as new SQL. |
| Supabase `docker/docker-compose.yml`, `docker/volumes/db`, and `docker/CHANGELOG.md` | Identify prerequisites supplied outside the Postgres migration tree, changed service configuration, coordinated image versions, and irreversible upgrade steps. |
| Auth and Storage migration sources at the old and proposed image releases | Confirm their unmodified migrations still work with the bootstrap's roles, schema ownership, extensions, and `DB_INSTALL_ROLES=false`. Identify prerequisites that must be applied before the new service starts. |

- Update the relevant inventory rows with pinned upstream links, rationale, and local SQL locations; update `NOTICE` when attribution changes. Record unresolved compatibility questions in the upgrade issue rather than silently treating them as exclusions.
- Append forward migrations for database changes. Do not edit, rename, delete, or insert before already-applied files. Checksums detect changes to local migration history; they do not detect missed upstream requirements. Existing databases need forward changes, not only an updated fresh-install baseline.
- Run the existing [Docker/Moto integration suite](../CONTRIBUTION.md#validation). It covers failed-transaction recovery, incompatible baseline rejection, immutable history, retries after service migrations, inherited permissions, and live PostgREST schema-cache refresh.
- Complete the [manual RDS acceptance](#manual-rds-acceptance) for fresh installation and upgrade. Ordinary PostgreSQL and Moto do not reproduce RDS's privilege model.

Back up RDS and plan recovery before upgrades. The pinned release includes [one-way Storage migrations](https://github.com/supabase/supabase/blob/self-hosted/v0.8.3/docker/CHANGELOG.md); ECS or CloudFormation rollback does not undo committed database migrations or secret writes.

## Manual RDS acceptance

Run only in a separately approved scratch AWS environment, alongside the [deployment acceptance checks](Deployment.md#manual-aws-acceptance). The Docker fixture's `postgres` is a real superuser; RDS's [`rds_superuser`](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Appendix.PostgreSQL.CommonDBATasks.Roles.rds_superuser.html) is not. Use the actual service credentials for permission checks: a successful administrator query does not demonstrate service access.

Record the source commit, source and target releases for upgrades, RDS engine/extension versions, effective parameter settings, image digests, and each outcome with sanitized SQL results or service errors. Keep credentials, tokens, query text containing application data, and operational evidence outside the repository. Record checks not run as unverified.

| Scenario | Required observation |
| --- | --- |
| Fresh installation | Bootstrap succeeds as the RDS master without true superuser privileges or manual SQL repairs. `auth` and `storage` belong to their respective service roles; `extensions` belongs to `postgres`. Required extensions are in their documented schemas. |
| Role boundaries | Of the six application/service roles, only `service_role` has `BYPASSRLS`; only `authenticator`, Auth, and Storage can log in. None has superuser, role/database creation, replication, or administrator membership. Inspect `pg_roles` and `pg_auth_members` after services start. |
| Role switching and administration | `authenticator` can assume the three API roles without inheriting them. Storage can assume `authenticator`. The direct `postgres` memberships for Auth/Storage end with `ADMIN TRUE, INHERIT FALSE, SET FALSE`; verify password refresh through the supported bootstrap path, not an added administrator grant. |
| Ownership and default privileges | Connect as Auth/Storage and verify service migrations succeed under their own schema owners. Inspect `pg_default_acl` and effective object privileges; creating a disposable public table must not automatically make it accessible to API roles. Migration-history tables and `supabase_aws` remain inaccessible to API roles. |
| Authorization | Using disposable rows and actual API credentials, verify anonymous denial, authenticated access to own rows only, cross-user denial, and trusted service-role access. Explicit table grants and RLS policies must both be effective. |
| Event triggers | Create, alter, and drop a disposable API table and alter a disposable type. PostgREST refreshes without restart; inspect both `ddl_command_end` and `sql_drop` triggers and Lambda/service errors. RDS permits administrator-created [event triggers](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.FeatureSupport.EventTriggers.html); support alone does not prove these functions work. |
| Upgrade and retry | Upgrade a scratch copy with representative data from the prior supported release. Only pending bootstrap migrations are appended; existing checksums, timestamps, service histories, data, and signing keys survive. Rerun deployment and deliberately rerun bootstrap through `CredentialRevision`: an unchanged deployment alone does not exercise Lambda retry. |
| Credential refresh and administration | Follow the [credential procedure](Credentials.md), then verify service reconnection and existing session refresh. If Studio is enabled, verify schema inspection and intended Storage administration without granting service-schema ownership or public access. |
| Recovery | Demonstrate snapshot restoration and reconnect the matching application/service version. Record any irreversible service migration and recovery steps before approving rollout. |

Compare fresh-install and upgraded states explicitly, especially conditional grants on service-owned tables. A skipped scenario or a manual repair is not a passing acceptance result; track it before rollout. Major PostgreSQL version upgrades require a separate review, including AWS's event-trigger restrictions; this stack currently targets PostgreSQL 17.
